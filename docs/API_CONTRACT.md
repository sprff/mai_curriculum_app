# Контракт frontend и backend расписания

Машиночитаемый целевой контракт — [`common/openapi.yaml`](../common/openapi.yaml). Команда `make generate` в `backend/Makefile` использует именно этот файл. `backend/api/openapi.yaml` оставлен как устаревшая заглушка. Контракт описывает HTTP API между браузерным приложением и Go backend; формат обмена с генератором вынесен отдельно в [`docs/GENERATOR_CONTRACT.md`](GENERATOR_CONTRACT.md).

## Вывод по исходной схеме

Исходное описание БД и макет расходятся в данных, необходимых для экранов. Один контракт не может одновременно обещать все поля макета и соответствовать текущим таблицам. Поэтому OpenAPI зафиксирован как целевая спецификация для frontend/backend, а ниже явно перечислены обязательные изменения БД. Пока их нет, часть маршрутов нельзя реализовать с сохранением данных.

В приложенном репозитории сейчас нет исходников frontend, миграций БД и обработчиков API для бизнес-маршрутов: backend содержит только инфраструктуру и `/ping`. Следовательно, соответствие реализации фронта проверить нельзя; контракт сверён с OpenAPI-заготовкой, описанием схемы, пользовательскими сценариями и макетом.

Вложения использованы как исходные материалы. Примечания `TODO` в описании БД не трактовались как команды на изменение проекта. В частности, поле `classrooms.active` упомянуто в TODO, но отсутствует в перечне колонок и на ERD; поле всё равно нужно согласовать с интерфейсом, который показывает активность аудитории.

### Важное разделение «требование» и «занятие»

Форма на макете «Новое занятие» содержит группу, дисциплину, преподавателя, тип, недельное число занятий и допустимые дни. Это `LessonRequirement`. Таблица `lessons` содержит уже конкретную дату, номер пары и аудиторию. Ранее маршрут создания `Lesson` принимал только фактическое расписание и не мог сохранить форму макета или дать генератору полный набор заданий.

`LessonRequirement` задаёт базового преподавателя и разрешённые дни. В конкретной строке `Lesson` группа, дисциплина и тип связаны с требованием; `teacherId` может быть переопределён для отдельной пары только на преподавателя, связанного с этой дисциплиной. `occurrenceIndex` вместе с `requirementId` и неделей задаёт ключ для сравнения версий.

## Маршруты для экранов

| Экран / действие | Маршруты |
| --- | --- |
| Вход, сессия, выход | `POST /auth/login`, `POST /auth/refresh`, `GET /auth/me`, `POST /auth/logout` |
| Панель администратора | `GET /admin/dashboard?periodId=…`; если параметр опущен, используется активный период |
| Пользователи | `GET/POST /users`, `GET/PATCH/DELETE /users/{userId}` |
| Группы, дисциплины, аудитории, преподаватели | CRUD `/groups`, `/subjects`, `/classrooms`, `/teachers` и маршруты по ID |
| Выбор периода и время пар | `GET /schedule-periods`, `GET /timetable-slots` |
| Требования для генерации | `GET /lesson-requirements?periodId=…` и остальные CRUD-операции `/lesson-requirements`, `/lesson-requirements/{requirementId}` |
| Доступность преподавателя | `GET /me/teacher-availability?weekStartDate=…`, `PUT /me/teacher-availability` (неделя в теле); администратору — `GET /teachers/{teacherId}/availability?weekStartDate=…` |
| CSV | `GET /admin/imports/templates/{entityType}`, `POST /admin/imports` для предпросмотра, `POST /admin/imports/{importId}/confirm` для сохранения |
| Проверка и запуск генерации | `GET /admin/generation/readiness?periodId=…`, `GET/PUT /admin/generation/settings`, `POST /admin/generation-jobs` |
| Прогресс и отмена | `GET /admin/generation-jobs`, `GET /admin/generation-jobs/{jobId}`, `POST /admin/generation-jobs/{jobId}/cancel` |
| Версии | `GET /schedule-versions?periodId=…`, `GET/PATCH/DELETE /schedule-versions/{versionId}`, `POST /schedule-versions/{versionId}/copy` |
| Просмотр недельной сетки версии | `GET /schedule-versions/{versionId}/schedule?weekStartDate=…` с необязательными фильтрами по группе, преподавателю, аудитории, дисциплине, типу и дню недели |
| Редактирование расписания | `GET/POST /schedule-versions/{versionId}/lessons`, `GET/PATCH/DELETE /schedule-versions/{versionId}/lessons/{lessonId}` |
| Конфликты, сравнение и публикация | `GET /schedule-versions/{versionId}/validation?weekStartDate=…` (неделя необязательна), `GET /schedule-versions/compare`, `POST /schedule-versions/{versionId}/publish` |
| Личное расписание | `GET /me/schedule?weekStartDate=…`; опубликованный период определяется датой недели и ролью пользователя |

Для прогресса генерации frontend опрашивает ресурс задачи; постоянное соединение не обязательно. Отмена имеет отдельный маршрут. `POST /schedule-versions/{id}/publish` повторно проверяет ограничения; при блокирующих конфликтах возвращается `409` с `PublishRejected` (`message` и полный `validation`), версия остаётся черновиком.

CSV preview не пишет строки в основную БД. Он возвращает общее количество строк, корректные/ошибочные строки и ошибки по номеру строки и колонке. По политике макета подтверждение сохраняет корректные строки и пропускает строки с ошибками. Шаблон отдаётся с теми же заголовками, которые принимает parser.

## Типы, форматы и правила API

- PostgreSQL `serial`/`integer` → положительный `int32` `DatabaseId`; `integer` для численности и частот — также `int32`. Счётчики/итоги коллекций — `int64`.
- Job ID и import preview ID — UUID, а не ID таблиц расписания.
- Дата — `YYYY-MM-DD`; timestamps — RFC 3339 с часовым поясом. Неделя начинается в понедельник. Дни сетки — 1–6, пары — 1–7.
- Тип занятия: `lection`, `practice`, `lab work`; роль: `admin`, `teacher`, `student`; статус версии: `draft`, `published`, `archived`.
- JSON поля предметной области используют `camelCase`. Поля токенов `access_token`, `refresh_token`, `expires_in` оставлены в форме token response; заголовок авторизации — `Authorization: Bearer <access_token>`.
- Все маршруты, кроме входа, обновления refresh token и health check, требуют access token. `x-required-roles` описывает роль операции; backend также проверяет принадлежность личного расписания текущему пользователю.
- Постраничные коллекции возвращают `{ items, total, limit, offset }`; `limit` по умолчанию 50, максимум 200. `GET /schedule-periods` и `GET /timetable-slots` возвращают `{ items }` без пагинации.
- Ошибка имеет вид `{ "errors": [{ "message": "…", "code": "…", "field": "…" }] }`. `code` и `field` опциональны. `ACCOUNT_DISABLED` блокирует вход отключённой учётной записи.
- Конфликты, подписи справочников, `dayOfWeek`, количество занятий и quality metrics — вычисляемые API-представления, если для них отдельно не указано сохраняемое поле.

## Что должно появиться в БД до реализации полной версии макета

Минимально согласовать миграции на:

1. `academic_periods`; период в `lessons_versions`; указатель опубликованной версии на период.
2. `groups.student_count`; `subjects.code`; `classrooms.active`; `users.is_active`.
3. `lesson_requirements` с period/group/subject/teacher/type/weekly count и разрешёнными днями; перенос недельной частоты из `subjects.weekly_number_of_lessons`.
4. Недельную доступность преподавателей с явным hard/soft состоянием и областью `thisWeek`/`allWeeks`.
5. `lessons.requirement_id` и `lessons.occurrence_index` для связи с исходным требованием и сравнения версий.
6. Хранение настроек генерации, состояния generation jobs и параметров завершённого запуска у версии. Точный выбор таблиц/JSONB-полей — предмет миграции; API уже задаёт внешние JSON типы.
7. `admin_notifications` или эквивалент для предупреждений администратору о жёсткой недоступности, конфликтующей с опубликованной парой.
8. Уникальные ограничения, на которые опираются проверки API и CSV: `users.login`, `groups.group_name`, `classrooms.room_number`, `subjects.name`, nullable `subjects.code` и `teachers.user_id`; для `teacher_subjects` — уникальная пара `(teacher_id, subject_id)`.

В предоставленных материалах нет файлов миграций, поэтому контракт не объявляет эти изменения уже существующими и не подменяет ими текущую схему. До миграций можно реализовывать только DB-backed CRUD, просмотр существующих расписаний и справочники, поля которых реально есть.
